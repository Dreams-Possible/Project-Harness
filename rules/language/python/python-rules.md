# Python 编码规范

## 命名规范
本部分定义 Python 代码必须遵守的命名和风格规范，基于 PEP 8 标准。

### 总览

| 类型 | 规范 | 示例 |
|------|------|------|
| 变量 | `snake_case` | `user_name`, `count` |
| 函数 | `snake_case` | `get_user_info()`, `calculate_total()` |
| 类 | `PascalCase` | `UserProfile`, `OrderManager` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT`, `DEFAULT_TIMEOUT` |
| 模块 | `snake_case.py` | `user_utils.py`, `data_processor.py` |
| 包 | `lowercase`（无下划线） | `mypackage`, `utils` |

### 变量命名

- 使用描述性名称，避免单字母变量（循环变量除外）
- 布尔变量使用 `is_`、`has_`、`can_` 前缀
- 私有变量使用单下划线前缀 `_private_var`

### 函数命名

- 使用小写字母和下划线
- 动词开头，清晰表达功能
- 私有函数使用单下划线前缀

### 类命名

- 使用 PascalCase（首字母大写）
- 避免缩写，使用完整单词
- 类名使用名词或名词短语

### 常量命名

- 全部大写，单词间用下划线分隔
- 定义在模块顶层

### 其他规范

- **异常类**：使用 `Error` 后缀，如 `ValueError`、`TypeError`
- **迭代器**：使用 `iter_` 前缀或 `__iter__` 方法
- **布尔方法**：使用 `is_`、`has_`、`can_` 前缀

## 编程习惯规范

本章定义的禁止项基于核心原则：**代码的可视性**如果某种语法会降低代码的可读性，即使它能减少代码量，也不允许使用。

### 禁止使用的高级语法或语法糖

| 类别 | 禁止/限制的语法 | 替代方案 |
|------|----------------|----------|
| 列表/字典/集合推导式 | 嵌套推导式、复杂条件推导 | `for` 循环 + `append()` |
| Lambda 表达式 | 复杂 lambda、多行 lambda | `def` 定义具名函数 |
| 三元表达式 | 嵌套三元、复杂条件 | `if-else` 语句 |
| 海象运算符 | `:=` 赋值表达式 | 先赋值，再使用 |
| 解包语法 | 复杂嵌套解包 | 逐个赋值 |
| 生成器表达式 | 复杂生成器 | 列表推导或 `for` 循环 |
| `*args` 和 `**kwargs` | 过度使用、类型不明确 | 显式参数 |
| 上下文管理器 | 复杂嵌套 | 分步处理 |
| 模式匹配 | `match-case`（Python 3.10+） | `if-elif-else` |
| walrus 运算符 | 赋值表达式 | 显式赋值 |
| `__import__` | 动态导入 | 标准 `import` 语句 |

### 1. 列表/字典/集合推导式
#### ❌ 禁止：嵌套或复杂的推导式
#### ✅ 推荐：使用 for 循环替代复杂推导式

### 2. Lambda 表达式
#### ❌ 禁止：复杂或多行 lambda
#### ✅ 允许：简单的 lambda
#### ✅ 推荐：使用具名函数替代复杂 lambda

### 3. 三元表达式
#### ❌ 禁止：嵌套或复杂的三元表达式
#### ✅ 允许：简单的三元表达式
#### ✅ 推荐：使用 if-else 语句替代复杂三元

### 4. 海象运算符（:=）
#### ❌ 禁止：所有赋值表达式
#### ✅ 推荐：先赋值，再使用

### 5. 解包语法
#### ❌ 禁止：复杂嵌套解包
#### ✅ 允许：简单的解包
#### ✅ 推荐：使用显式赋值替代复杂解包

### 6. 生成器表达式
#### ❌ 禁止：复杂的生成器表达式
#### ✅ 允许：简单的生成器表达式
#### ✅ 推荐：使用 for 循环替代复杂生成器

### 7. `*args` 和 `**kwargs`
#### ❌ 禁止：过度使用或类型不明确
#### ✅ 允许：合理的 *args 和 **kwargs 使用
#### ✅ 推荐：优先使用显式参数

### 8. 上下文管理器
#### ❌ 禁止：复杂嵌套的上下文管理器
#### ✅ 允许：简单的上下文管理器
#### ✅ 推荐：分步处理复杂资源

### 9. 其他禁止或限制的语法
#### ❌ 禁止：链式比较
#### ✅ 推荐：使用显式比较

#### ❌ 禁止：多重赋值
#### ✅ 推荐：逐个赋值

#### ❌ 禁止：过于复杂的列表推导式中的条件表达式
#### ✅ 推荐：使用 for 循环和简单的条件判断

#### ❌ 禁止：`__import__()` 动态导入
#### ✅ 推荐：使用标准 `import` 语句或 `from ... import ...`
#### 说明：`__import__()` 降低代码可读性，IDE 无法提供补全和静态检查，除非有明确的延迟加载需求（如循环依赖），否则一律使用标准导入

### 总结原则

1. **可读性优先**：代码首先是写给人看的，其次才是给机器执行的
2. **新手友好**：确保团队中的新手能够快速理解代码逻辑
3. **避免炫技**：不要为了展示语言技巧而使用复杂语法
4. **显式优于隐式**：明确表达意图，不要依赖语言的隐式行为
5. **简单胜于巧妙**：选择简单直接的实现方式，即使它不是最"优雅"的

**记住：如果一种语法需要你停下来思考才能理解，那么它可能不适合在团队代码中使用。**

## 静态检查配置

本规范对应的 Ruff 配置文件与本文件位于同一目录。

该配置是默认基线。项目已有静态检查配置时，优先使用项目自身配置；项目未提供配置时，再使用这份默认配置。

### 使用方法

```bash
# 检查当前目录
ruff check .

# 检查指定文件
ruff check path/to/file.py

# 自动修复可修复的问题
ruff check --fix .
```

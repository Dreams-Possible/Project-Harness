# project-scan 技能说明

## 使用场景

需要根据目录结构生成或更新项目架构快照时使用。

---

## 技能定位

本技能是**手动触发的架构扫描工具**。它通过扫描项目目录结构，推断出当前项目的模块划分和架构层次，并生成架构概览。

设计约束：
- **只扫描目录结构和模块组织**，不读取任何源代码文件的具体内容
- **与具体代码完全解耦**：仅从目录名称、文件名称推断架构语义
- **默认只输出概览**，如需保存，由用户指定写入位置
- **适用于任意项目**，不绑定任何编程语言

---

## 执行流程

### 步骤 1：列出项目根目录的直接子目录（第一层）

使用 shell 命令列出根目录下的直接子目录。

### 步骤 2：对每个非排除目录，列出其直接子目录（第二层）

目的：了解每个顶层模块的内部组织方式，为推断架构层次提供依据。

对步骤 1 所得到的每个目录，再列出其直接子目录（只到第二层，不递归更深）。

### 步骤 3：推断架构层次

根据目录名称的命名语义，将各顶层目录归类到架构层次中。

常见命名语义参考：

| 命名关键词 | 推断的架构职责 |
|-----------|--------------|
| `ui`、`views`、`pages`、`screens`、`widgets`、`components` | UI / 视图层 |
| `app`、`application`、`controller`、`handlers` | 应用层 / 控制层 |
| `services`、`usecases`、`domain`、`business` | 业务逻辑 / 服务层 |
| `models`、`entities`、`data`、`schema` | 数据模型层 |
| `infra`、`infrastructure`、`adapters`、`drivers`、`hw`、`hardware` | 基础设施 / 驱动层 |
| `proto`、`protocol`、`comm`、`network`、`api` | 通信 / 协议层 |
| `config`、`settings`、`conf` | 配置层 |
| `utils`、`tools`、`helpers`、`common`、`shared`、`core` | 工具 / 公共层 |
| `tests`、`test`、`__tests__`、`spec` | 测试目录（不计入业务层次） |
| `docs`、`doc`、`documentation` | 文档目录（不计入业务层次） |
| `scripts`、`bin`、`cmd` | 脚本 / 入口目录 |
| `assets`、`static`、`resources`、`res` | 静态资源目录 |

推断规则：
- 识别哪些目录属于同一架构层（例如 `views/` 和 `widgets/` 都属于 UI 层）
- 根据命名语义判断层次高低（UI 层最高，基础设施层最低）
- 层次之间的依赖方向：高层依赖低层（单向）

### 步骤 4：生成架构概览

按以下格式生成架构概览：

```markdown
# 项目架构快照

> 由 project-scan 技能自动生成，不代表代码实际运行关系，仅反映目录结构语义。
> 如需更新，重新执行扫描。

## 顶层模块列表

| 目录名 | 推断职责 |
|--------|---------|
| xxxx/  | xxxxxx  |
...

## 推断的架构层次

（根据命名语义，将顶层模块归类到对应的架构层）

层次 N（最高层）：目录A, 目录B
  ↓
层次 N-1：目录C, 目录D
  ↓
...
层次 1（最底层）：目录X, 目录Y

## 各层职责说明

**层次名称**：
- 包含：[目录列表]
- 推断职责：[语义描述]

...

## 备注

记录推断时的不确定项或需人工确认的模块归属
```

### 步骤 5：向用户报告扫描结果

扫描完成后，向用户输出简要报告，说明：
- 发现了哪几个架构层次（层次名称和数量）
- 共扫描到多少个顶层模块
- 架构概览已生成；如需保存，可由用户指定位置

---

## 注意事项

- 本技能的推断仅基于目录命名语义，可能与实际代码依赖关系不符
- 如发现推断有误，修正目录结构或重新执行扫描即可
- 本技能不检测跨层调用等运行时问题，如需深度依赖分析需人工或额外工具介入
- 只有在用户明确指定位置后，才可将概览写入文件

# 核心规则

## 设计哲学

1. **面向对象** — 凡不属于语言基本数据类型的数据集合，都应封装为对象，统一通过方法操作
2. **最小实现** — 抓主要矛盾，先实现核心功能最小版本，快速成型后逐步扩展
3. **善于减法** — 选择并非越多越好，适当舍弃使意图更清晰，先迈出第一步

## 设计原则

### 模块化
- 模块只暴露明确定义的公共接口，内部实现对外不可见
- 模块间只通过抽象接口层交互，禁止直接访问对方内部
- 接口定义优先于实现
- 每个模块职责单一
- 模块内高内聚，模块间低耦合
- 接口即契约，修改须评估对调用方的影响

### 层次架构
- 层间只允许垂直单向依赖（高层→低层，禁止反向）
- 禁止跨层调用，每层只能调用相邻下一层
- 关注点分离，每层只处理自己的核心问题
- 数据流单向，禁止层间共享可变状态
- 错误边界清晰，无法处理的错误向上层传递

### 最简设计
- 代码简洁易读，新手也能基本读懂
- 避免仅为简洁引入的高级语法糖，优先显式写法
- 不引入不必要的第三方依赖，优先使用标准库
- 引入新依赖前必须明确获得批准

## 好的习惯

1. **拒绝冗余依赖** — 每引入新依赖必须有明确需求，不再需要时及时移除
2. **关键注释** — 核心逻辑、流水线步骤应通过注释补充说明
3. **配置集中管理** — 配置参数统一存放配置文件，禁止硬编码
4. **规范命名** — 遵循语言社区通用命名规范，名称清晰表达用途
5. **错误传递** — 函数必须传递错误信息，调用者必须先检查错误再使用返回值
6. **插件化复用** — 重复逻辑抽象为插件，相似场景下复用
7. **意图明确** — 需求模糊之处立即提出并确认
8. **先想后做** — 动手前先走思考流程：识别实体 → 划分边界 → 定义接口 → 再写实现

## 设计思维

动手写代码前，先完成以下思考流程：

1. **拿到需求**：明确目标、约束条件和不做什么。
2. **识别核心实体**：从需求中提取关键概念，并明确各自的职责边界。
3. **划分模块边界**：按单一职责拆分模块，确定模块间的依赖方向。
4. **定义接口契约**：先确定模块暴露和隐藏的内容，再考虑内部实现。
5. **编写实现**：前四步明确后，再开始实现。

## 瑞士军刀

1. **先答后做** — 所有需求先以自然语言回答，再执行操作
2. **确认意图** — 用户有明确意图时，先复述理解并说明行动方案，获确认后再执行
3. **意图不明必须问** — 不清楚用户意图时，明确询问，禁止猜测，等待回应后再行动
4. **明确指令也要确认** — 即使指令明确，也须先告知方案，得到确认后才能继续
5. **读自由，写受限** — 读操作可自由执行，写操作必须获得用户明确允许
